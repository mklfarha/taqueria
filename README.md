# Taquería Tracker

A small REST API for keeping score on taquerías — where they are, what they
charge for each type of taco, and whether a given visit was worth it.

Three things get tracked: **taquerías** (name, colonia, house specialty),
**tacos** (one price per taco type, per taquería) and **visitas** (a date, a
verdict, and optional notes). Built to answer questions like *"where is the
cheapest suadero in the Roma?"* and *"did I already decide this place wasn't
worth returning to?"*

Written in Go, backed by MySQL, deployed to Kubernetes.

## Generated with nuzur

Most of this repository is **generated by [nuzur](https://nuzur.com)
`go-code-gen`** from a schema defined in nuzur — entities, enums,
relationships and indexes. From that schema it produces the entity structs,
validation, the SQL schema and queries, the repository layer, the REST handlers
and the OpenAPI spec, plus the Dockerfile, Helm chart and CI workflows.

What that means if you're reading or contributing:

- **Generated files say so.** Every one carries a
  `Code generated by nuzur go-code-gen. DO NOT EDIT.` marker near the top, and
  all 124 of them are listed in `.nuzur-codegen-manifest.json`. Edits are
  overwritten on the next generation run.
- **Schema changes belong in nuzur, not in Go.** Adding a field or an entity by
  hand-editing the structs or `create.sql` won't survive regeneration and won't
  reach the database.
- **`app/` is the hand-written zone.** It is scaffolded once and never
  overwritten — custom REST routes go in `app/rest.go`, background workers in
  `app/worker.go`. Adding an endpoint there needs no code generation.

`AI.md` is the long-form version of the above, aimed at coding agents.

## Data model

| Entity | Fields | Notes |
|---|---|---|
| `taqueria` | `name`, `colonia`, `especialidad` | `name` is unique; `especialidad` is a `TipoTaco` |
| `taco` | `taqueria_uuid`, `tipo`, `precio` | unique per `(taqueria, tipo)` — one price per taco type |
| `visita` | `taqueria_uuid`, `fecha`, `veredicto`, `notas` | indexed by `(taqueria, fecha DESC)` for recent-first lookups |

Every row has a UUID `id` plus `created_at` / `updated_at`. Tacos and visitas
are children of a taquería and cascade on delete.

**`TipoTaco`** — `pastor`, `suadero`, `campechano`, `bistec`, `lengua`,
`tripa`, `chorizo`, `canasta`

**`Veredicto`** — `imperdible`, `bueno`, `pasable`, `nunca_mas`

## API

REST, under `/v1`. Full CRUD on all three collections:

```
GET    /v1/taquerias          POST   /v1/taquerias
GET    /v1/taquerias/{id}     PATCH  /v1/taquerias/{id}     DELETE /v1/taquerias/{id}

GET    /v1/tacos              POST   /v1/tacos
GET    /v1/tacos/{id}         PATCH  /v1/tacos/{id}         DELETE /v1/tacos/{id}

GET    /v1/visitas            POST   /v1/visitas
GET    /v1/visitas/{id}       PATCH  /v1/visitas/{id}       DELETE /v1/visitas/{id}
```

Plus `GET /healthz`, `GET /v1/openapi.yaml` (the full spec), and an info page at
`/` describing the deployment.

List endpoints accept `filter`, `order_by`, `page_size`, `page_token`,
`include_fields`, `exclude_fields` and `skip_cache`. Paging is opaque-token
based; responses carry `next_page_token` when more rows remain.

```bash
curl 'http://localhost:8080/v1/taquerias?order_by=name&page_size=10'
curl 'http://localhost:8080/v1/tacos?filter=tipo=pastor'

curl -X POST http://localhost:8080/v1/visitas \
  -H 'Content-Type: application/json' \
  -d '{"taqueria_uuid":"<uuid>","fecha":"2026-08-18","veredicto":"imperdible","notas":"el pastor"}'
```

## Running locally

Requires Go 1.26+ and a MySQL database.

```bash
# 1. create the schema
mysql -u root taqueria < core/repository/sql/schema/create.sql

# 2. point config at your database
cp config/base.yaml config/local.yaml
$EDITOR config/local.yaml          # fill in the db block

# 3. run
CONFIG=./config ENV=local go run .
```

Config is layered: `base.yaml` loads first, then `<ENV>.yaml` on top, so
`local.yaml` only needs the keys it overrides. `CONFIG` may be a directory or a
comma-separated list of files. HTTP listens on `8080`.

Note that `config/base.yaml` is generated and ships with placeholder values
(`<< Database Host Here>>`) — real credentials belong in an env-specific file,
which `.gitignore` keeps out of git.

With Docker:

```bash
docker build -t taqueria .
docker run -p 8080:8080 -e CONFIG=/root/config -e ENV=prod taqueria
```

## Deployment

Two GitHub Actions workflows publish to GHCR on push to `main`:

- `ghcr.io/mklfarha/taqueria/taqueria` — the container image, tagged `latest`
  and `sha-<commit>`
- `ghcr.io/mklfarha/helm/taqueria` — the Helm chart

The chart in `.helm/taqueria` deploys to Kubernetes behind an nginx ingress with
cert-manager TLS. Chart defaults live in `values.yaml` (generated, rewritten
every run); hand-tuning goes in `values-custom.yaml`, which is generated once
and then left alone.

Database credentials are deliberately **not** part of the release — they are
read from a credentials file mounted from the node, so they never land in Helm's
stored values. See `.helm/taqueria/templates/NOTES.txt` for the setup.

## Layout

```
main.go               fx wiring — config, core, REST server, custom routes
app/                  hand-written zone: custom routes and workers
config/               layered YAML config
core/module/          business logic per entity (upsert, fetch, list, delete)
core/repository/      sqlc-generated queries, SQL schema, list/filter builder
entity/               entity structs, JSON mapping, validation
enums/                TipoTaco, Veredicto
rest/server/          generated HTTP handlers, router, middleware
rest/openapi.yaml     API specification
.helm/taqueria/       Helm chart
```

## Status

A personal project, run for one person's taco habit. Authentication is
currently disabled — the generated `AuthMiddleware` passes every request
through — so anything with network access to the deployment can write to it.
Fine for the current setup; worth knowing before pointing anything else at it.
